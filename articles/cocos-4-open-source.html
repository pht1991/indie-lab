COCOS 4 Open Source: Time to Leave Cocos Creator 3.8?

By Haitao Pan · Game Developer & Studio Owner · 9 min read

TL;DR: I run a Cocos Creator 3.8 WeChat mini-game in production. COCOS 4 — fully open-sourced under MIT in early 2026 — is the biggest shift in the Cocos ecosystem in years, but it is not a "drop 3.8 now" signal, especially for mini-game developers. The engine and editor have been split apart (the new IDE is called PinK), WeChat support is rolling out gradually, and 3.8 is still the more stable bet for my use case. Here's the honest breakdown and the call I'm making.

1. The headline: what actually shipped

Cocos was acquired by the Chinese gamification company SUD for around $72M in November 2025. On January 5, 2026, SUD announced that COCOS 4 is fully open source under the standard MIT license — every commercial clause from the old Cocos Creator has been removed. The public repositories include the engine core (github.com/cocos/cocos4), the cross-platform code, the cocos-cli, and a full headless IDE mode. There is no commercialization target behind it; SUD's stated motive is reaching more developers and feeding more game content into its own ecosystem.

For a solo dev, "MIT, no strings" is a genuinely big deal. But the headlines skipped the part that actually affects your day-to-day: this isn't a normal version bump.

2. The part that confuses everyone: it's not "Cocos Creator 4"

Through versions 1.x, 2.x, and 3.x, "Cocos Creator" meant one thing: the engine and the editor bundled together. COCOS 4 breaks that apart:

  • COCOS = the engine only (version 4 is just the latest release number).
  • PinK = the new standalone IDE. The visual editing features from Cocos Creator migrate here over time.
  • cocos-cli = headless mode. Core editing functions move to CLI-accessible headless operations that become part of the engine core.

So when you search "Cocos Creator 4," what you actually mean is COCOS 4 (engine) + PinK (IDE). Same lineage, different packaging. If you're evaluating it, search "COCOS 4" — you'll find the right repos and docs.

3. What changed that a solo dev actually cares about

  • MIT, no commercial clauses. You can read, patch, and even fork the engine into your own modified build. For a one-person team that's been burned by licensing surprises elsewhere, this removes a whole class of risk.
  • AI-native by design. JavaScript and TypeScript stay the primary languages, and new capabilities are delivered as MCPs or Agents rather than traditional libraries — UI components, for example, ship as fully deliverable Agents, not call-and-use widgets.
  • Lighter and more modular. The stated goal is "faster, smaller, more efficient," meant to run on any device with a screen.
  • Cross-platform, but read the fine print. Native platforms are covered across the board; mini-game platform support rolls out gradually, and Steam-class native targets are on the roadmap.
  • Forward compatibility. COCOS 4 is an evolution of 3.x, follows SemVer, and keeps a minimum six-month deprecate-to-remove window.

4. What it means for a solo indie

The upside is real:

  • Zero licensing anxiety, forever.
  • You can fix engine bugs yourself instead of waiting on a vendor.
  • An open PR flywheel — more contributors, faster fixes.
  • AI-tooling that actually understands the engine because the source is open.

But the open questions matter more for someone shipping today:

  • PinK is a new IDE. The Cocos Creator editor you know (and that I've shipped two projects on) is battle-tested. PinK is where visual editing is migrating — its maturity is unproven.
  • Migration has a cost. API cleanup and the deprecation cycle mean a 3.x project won't lift-and-shift for free.
  • The WeChat mini-game target is "gradual." For me this is the dealbreaker line — see below.

5. My call as a Cocos Creator 3.8 developer

My constraints are specific: my game is a WeChat mini-game, it's in production on 3.8, and all my hard-won optimization work — engine subpackaging, asset splitting, a runtime PerfTier — is built on 3.8 (I wrote it up in my bundle-size teardown). COCOS 4's WeChat support is still rolling out. Migrating now trades proven stability for an "open source" label I don't strictly need yet.

So my decision:

  • Stay on 3.8 for anything already shipping to WeChat — it's the stable, complete path today.
  • Evaluate COCOS 4 for a new project that needs native/Steam targets, a hard MIT requirement, and can tolerate an early PinK.
  • Watch, don't rush. The six-month deprecation window and the gradual mini-game rollout both reward patience.

6. If you're still choosing an engine

None of this changes the core advice in my Cocos vs Unity vs Godot breakdown: for a WeChat or HTML5 mini-game, the 3.x line's native build pipeline and tiny first-load package are still unmatched. COCOS 4 makes the long-term future of that engine more open and more interesting — it just isn't the tool you need to switch to this afternoon. Decide by your distribution channel first; version number second.
